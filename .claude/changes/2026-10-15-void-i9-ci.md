# void-i9-ci — I-9: CI runs in Void's own image

## What changed
- `.github/workflows/ci.yml`:
  - `lint` and `tests` are unchanged (Ubuntu runner, distro-agnostic);
  - `build-suckless` and the new `package-names` (replacing
    `install-dry-run`) run in `ghcr.io/void-linux/void-glibc-full:latest`,
    one leg each;
  - each container job starts with a `shell: sh` step (`xbps-install -Syu
    xbps`, `-yu`, then bash + git), because the image has neither; job
    default shell is bash;
  - build deps come from build.lst via xbps-install; the ASan runtime is
    libsanitizer-devel; Void names for the dwm-runtime tools;
  - `package-names` runs `xbps-query -R` on every list name against the live
    index.
- `.github/workflows/install-container.yml`:
  - the same image and bootstrap; the dnf drop-in assert is gone;
  - new asserts: every `SERVICE<TAB>` row is linked in
    /etc/runit/runsvdir/default and ly is among them; LYBUILD paths present,
    /usr/bin/ly executable; the coverage report is rewritten;
  - the SERVICE and LY greps are tab-anchored (reviewer BLOCK: `^SERVICE`
    matched SERVICEOFF, and `^LY` matched LYBUILD);
  - timeout 40.
- Two fixes found by running the installer in the real image:
  - `scripts/install-services-runit.sh`: runit_service falls back to
    /etc/runit/runsvdir/default when /var/service is not a directory (it
    links into /run, which only a booted system has; chroots too);
  - `scripts/drivers-firmware.sh`: rebuilds the initramfs of every INSTALLED
    linuxX.Y package (from xbps-query -l). `uname -r` named the host's kernel
    in a container ("linux7.2").
- Tests: ci-build-deps shims xbps-install; services-runit gains a resolution
  check (no write); drivers fakes `xbps-query -l`, adds a no-kernel case, and
  seals the real uname in.
- Docs: CLAUDE.md (tech stack + map), CONTRIBUTING (index snapshot replaces
  the Fedora pin), TESTING (container section, coverage table), HARDWARE,
  CHANGELOG, scope.

## Key Technical Decisions
- **One leg, the latest image:** Void is rolling; the Fedora
  oldest-supported pin has no meaning here. Snapshot staleness is what ages
  instead, caught by `package-names` plus the 90-day warning.
- **The jobs were run locally before writing their claims**, with docker and
  the same image, extracting the steps from the YAML.

## Assumptions Made
- (B) GitHub's container runner picks bash for steps once bash exists, with
  the explicit `defaults.run.shell: bash` and a `shell: sh` first step. Not
  run on GitHub itself yet: the branch is not pushed.
