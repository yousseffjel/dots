# ly-theme
Date: 2026-10-12
Files: 20 | Lines: +~1030/-9 (422 of them the captured ly config fixture)

## What changed
- New `scripts/theme/ly-theme.sh` (`dots login-theme [<theme>]`). It edits
  four keys of `/etc/ly/config.ini` in place:
  - `fg` = `0x00` + the theme's `txt1`
  - `border_fg` = `0x00` + the theme's `1xa7` (the same keys as dwm's text and
    selected border)
  - `bigclock = en`
  - `hide_version_string = true`

  It writes with `cp` onto the existing file, so the owner, mode and SELinux
  label (`etc_t`) are kept. Before the first write that is certain to happen,
  it saves ly's original lines to `~/.local/state/dots/ly-config.orig` and adds
  an `LY` manifest row. `--restore` writes those lines back and `--dry-run`
  writes nothing. It never prompts without a TTY: it tries `sudo -n`, and if
  that is refused it exits 3 and names the command to run. A key that ly lacks
  is reported and never appended.
- Callers:
  - the services stage, after enabling ly (the active theme, else dark);
  - `theme-apply.sh` on a static switch only (exit 3 sends a notification
    instead of hanging a keybinding);
  - `dots login-theme`, a new SUBCOMMANDS row (the help column is widened to
    12 characters for the name);
  - `uninstall_ly`, in `uninstall-theme.sh`, which runs before
    `uninstall_packages`.
- `tests/ly-theme.sh` runs against `tests/fixtures/ly-config-1.4.0.ini`, the
  real `/etc/ly/config.ini` copied from the Fedora 44 VM (ly-1.4.0-2.fc44).
  `tests/fixtures/` is new and outside the depth-1 test glob.
- `theme-identity.sh` and `wallpaper-default.sh` now point `DOTS_LY_CONFIG` at
  a sandbox, so the `theme-apply.sh` runs they make can never reach a host's
  ly config.
- The `install-container.yml` assert step checks for an `LY` row and
  `bigclock = en` in the real `/etc/ly/config.ini`. It was extracted and
  shellchecked by hand, as its header requires.
- Docs: THEMING.md has a new "The login screen (ly)" section plus an uninstall
  note. Also CHANGELOG `[Unreleased]` → Added, and the CLAUDE.md project map.

## Why
The user asked to "work on ly theme". Decisions (asked, Type A): write at
install and on every static theme switch (one sudo per switch); the look is
clean with no animation and the big clock on.

## Assumptions
- Type B: the colour mapping. Text is `txt1` and the border is `1xa7`, the same
  keys as `dwm.normfgcolor` / `dwm.selbordercolor`, so the login screen matches
  the desktop's focused window. If wrong: change the `WANT` array in
  ly-theme.sh.
- Type B: the background stays `0x00000000` (the terminal default), and
  `error_fg` keeps ly's red. A palette has no "error" colour.
- Type B: wallbash never writes ly, because every wallpaper change would be
  another root write.
- Type C: `ly-config.orig` lives in the manifest state dir, so a declined
  restore is followed by `uninstall_state` removing it, which is the user's
  choice.
