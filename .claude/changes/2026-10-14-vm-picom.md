## What changed
- `scripts/drivers-detect.sh`: `drivers_is_vm` (`systemd-detect-virt --vm
  -q`, where a container is not a VM; the `DOTS_VIRT` test override counts
  as a VM unless it is none/unknown). `drivers_chassis` answers **vm**
  first, before laptop, battery or desktop, and `drivers_chassis_why` names
  the hypervisor: `vm (kvm, chassis type 1)`.
- New `config/dwm/bin/dwm-picom`. `backend` prints
  `<xrender|glx><TAB><why>`: VM → xrender always; bare metal → glx only on a
  direct, non-llvmpipe/softpipe/swrast renderer; xrender otherwise,
  including when glxinfo or timeout is missing or GL hangs (5 s). `start`
  (the default) execs picom with that backend unless picom is running.
- `install-session-template.sh`: the compositor block runs `dwm-picom &`,
  falling back to `picom --backend xrender &` when dwm-picom is not on PATH.
  The inline glxinfo probe is gone from new autostart.sh files.
- `install-session-report.sh` `session_report_picom_probe`: an existing
  autostart.sh that lacks dwm-picom is told to replace its picom lines with
  `dwm-picom &`. A file with no backend choice at all also gets the freeze
  warning.
- `doctor-session.sh` `check_picom_backend`: compares picom's running
  backend with `dwm-picom backend`. A match is ok with the reason; xrender
  where glx would do is ok with a note; glx (or picom.conf's default) where
  xrender is needed is a **warn** naming `dwm-picom &`.
- Tests: `tests/picom-backend-probe.sh` rewritten (a dwm-picom matrix: 7
  bare-metal cases, 4 VM cases, start, the template block with and without
  dwm-picom, report cases). New vm cases in drivers-cases. Doctor picom
  cases. The doctor laptop block runs with `FAKE_VIRT=none`.
- Docs: THEMING.md (picom bullet), HARDWARE.md (vm), TESTING.md,
  CLAUDE.md (rule 6 picom sentence, Roadmap status, dwm/bin list),
  CHANGELOG (Added: vm; Changed: dwm-picom).

## Why
The user asked (2026-10-14) for VMs in the PC/laptop checker and for picom
to choose its backend from the hardware automatically. It already probed GL,
but the probe was pasted into the user-owned autostart.sh, so no fix could
reach an existing install (rule 6). And a VM with 3D passed through (virgl)
still got glx, the backend that froze the first VM install.

## Key Technical Decisions
- **`vm` as a chassis result, winning over everything** (user, 2026-10-14):
  a hypervisor can fake a chassis type or a battery.
- **dwm-picom script plus the rule "VM → xrender"** (user, 2026-10-14). It
  lives in the linked config/dwm/bin so it updates with dots. autostart.sh
  only calls it.
- A VM gets xrender even with working 3D. The guest GL stack is where glx
  hung before, and the shipped picom.conf uses no glx-only effect.
- Existing autostart.sh files are reported to, never rewritten (rule 6).
  Their inline probe already gives xrender on a VM without 3D, so the VM is
  safe meanwhile.
