## What changed

  - **Choosing encryption.** The dialog question defaults to No; a Yes asks
    for the passphrase twice. An unattended run sets `LUKS_PASSFILE`.

## Why

Scope J, J-4: encryption is optional (decision 3), with only root encrypted
and dracut unlocking it (decision 6) so that GRUB needs no cryptodisk
support and there is one prompt per boot.

## Key Technical Decisions

- **Unattended passphrase: `LUKS_PASSFILE`** (user, decision 13). The file
  must be root's and mode 600. The answers file stays hashes-only.
- **Dialog default: No** (user, decision 14).
- **No crypttab entry** (user, 2026-10-16). In runit-void-20250212_4,
  `/etc/runit/crypt.awk` runs `cryptsetup luksOpen` on every crypttab line
  with no check for a device that is already open. dracut opens root first.
  base-files' crypttab is comments only and itself says not to list `/`.
- **DEVIATION: `GRUB_CMDLINE_LINUX`, not `_DEFAULT`** as the scope row
  says. The UEFI VM showed that grub-mkconfig gives `_DEFAULT` only to the
  normal entries, so the recovery entries had no `rd.luks.uuid=`. Void ships
  no `GRUB_CMDLINE_LINUX` line, so one is appended, and only when encrypting.
- **The live mapping is named `luks-<UUID>`**, the same name the booted
  system uses. Anything grub-mkconfig or xgenfstab read on the live side
  then names the right device. fstab and GRUB use the ext4 UUID anyway.
- **The answers win on a re-run.** A re-run resumes only when the root
  mounted from the earlier run matches this run's choice: plain on
  `dots-root`, or a mapping on `dots-root` that this run's passphrase opens
  (`--test-passphrase`). Anything else lays the disk out again. The erase
  was already confirmed.
- **The passphrase goes in with no newline**, exactly as it is typed at the
  boot prompt. `cryptsetup --key-file -` reads its input whole, so a
  trailing newline would become part of the key.
- Explicit `add_dracutmodules+=" crypt "`. Void's dracut is not hostonly, so
  installing cryptsetup alone would already include the module (read from
  70crypt's `check()`). The explicit line makes dracut fail loudly if the
  module cannot be built.

## Assumptions Made

- Type B: the dialog Yes runs `loadkeys` with the chosen keymap, and
  `rd.vconsole.keymap=` is set, so the passphrase is typed with the same
  layout at install and at boot. Verified with `us` only.
- Type B: cryptsetup goes into every target, not only encrypted ones. That
  keeps one package list and makes a hand-opened `--target` LUKS root work
  (`live_luks_backing` reads it from the mount).
- Type B: `--skip-dots` closes nothing. It unmounts nothing either, and the
  reboot tears the mapping down.

## Research (method)

- Void repodata (`x86_64-repodata`, 2026-10-16): base-system-0.114_2 does not
  pull in cryptsetup. libcryptsetup pulls in device-mapper (dmsetup, needed
  by dracut's dm module).
- dracut-112_1 package: `/etc/dracut.conf` is empty (not hostonly).
  `70crypt/module-setup.sh` `check()` needs cryptsetup and has no further
  host requirement unless hostonly. `20i18n` in non-hostonly mode installs
  every keymap and honours `rd.vconsole.keymap`.
- runit-void-20250212_4: `03-filesystems.sh` runs `crypt.awk` on
  `/etc/crypttab`; read in full.

    passphrase was entered twice.

  - Booted the `linux-lts` 6.12.113 entry: one prompt, ly, the swapfile and

- Not verified: bare metal, Secure Boot, NVMe (tests only), a keymap other
